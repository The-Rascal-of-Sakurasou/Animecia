# ANIXIA ジャンル体系（設計ドラフト）

- 状態：設計案。正式確定・本番DB反映前
- 更新日：2026-11-21
- 対象：ANIXIAに収録する日本のアニメ作品
- 目的：作品の内容を一貫した基準で分類し、検索性を高める。作品数を機械的に均等化することは目的にしない。

## 1. 設計原則

1. ジャンルは作品の主要な内容・物語上の性質を表す。
2. 舞台、設定、物語展開、対象年齢、作品形式は原則としてジャンルと分離する。
3. 1作品に複数ジャンルを付与できる。ただし、単に要素が登場するだけでは付与しない。
4. ジャンルの粒度をそろえ、同義語・重複分類を増やさない。
5. 少数作品にしか該当しない特徴は、独立ジャンルにせずサブジャンルまたはタグとして扱う。
6. 作品数の均等化を目的に、意味の異なるジャンルを統合したり、定義を変更したりしない。
7. 外部データのジャンルは出典情報として保持し、ANIXIA独自ジャンルへ自動的に同一視しない。対応関係は個別に検証する。

## 2. 大ジャンル候補（17分類）

| ID案 | 日本語名 | 定義・付与基準 |
|---|---|---|
| action | アクション | 戦闘、格闘、追跡、身体的な対決など、動的な行動・対決が作品の主要な魅力または物語展開を担う。 |
| adventure | アドベンチャー | 未知の場所・世界の探索、旅、冒険、発見や困難への挑戦が物語の中心となる。 |
| comedy | コメディ | 笑い、ギャグ、ユーモアを生み出すことが作品の主要な目的・特徴となる。 |
| drama | ドラマ | 人間関係、葛藤、心理、社会的問題、人生の変化などを継続的に描くことが中心となる。 |
| romance | 恋愛 | 恋愛感情や恋愛関係の形成・変化が物語の重要な軸となる。恋愛要素が背景にあるだけでは付与しない。 |
| science_fiction | SF | 科学・技術・未来社会・宇宙・人工知能など、科学的または技術的な仮説・設定が物語の重要な基盤となる。 |
| fantasy | ファンタジー | 魔法、神話的存在、超自然的な力、架空世界など、現実の自然法則を超える設定が物語の重要な基盤となる。 |
| mystery | ミステリー | 謎、事件、秘密、手掛かりの提示と真相解明・推理が物語の中心となる。 |
| suspense | サスペンス | 危機、緊張、不安、追跡、心理戦など、先行きへの緊迫感を持続させる構成が主要な特徴となる。 |
| horror | ホラー | 恐怖、不気味さ、怪異、脅威などを観客に感じさせることが主要な目的・特徴となる。 |
| sports | スポーツ | スポーツ・競技への参加、練習、試合、勝敗、競技者としての成長が物語の中心となる。 |
| slice_of_life | 日常 | 日々の生活、身近な出来事、生活の変化や交流を中心に描き、日常そのものを主な見どころとする。 |
| youth | 青春 | 青年期・学生時代の成長、友情、進路、自己形成、仲間との経験などが作品の中心となる。単に登場人物が学生というだけでは付与しない。 |
| music_entertainment | 音楽・芸能 | 音楽活動、演奏、歌唱、アイドル、芸能活動、舞台パフォーマンスなどが物語の中心となる。 |
| historical | 歴史・時代劇 | 実在の過去の時代・歴史的事件・歴史上の人物、または歴史考証を主要な基盤とする。架空世界の古風な設定だけでは付与しない。 |
| military_war | 戦争・ミリタリー | 戦争、軍事組織、作戦、兵器、軍隊生活、戦略・戦術などが物語の中心となる。単発の戦闘描写だけでは付与しない。 |
| mecha | ロボット・メカ | ロボット、搭乗型兵器、機械装置などの設計・運用・戦闘・存在が作品の中心的な特徴となる。 |

### 2.1 複数ジャンルの付与例

- SFロボット作品：SF + ロボット・メカ。戦争が中心なら戦争・ミリタリーも付与。
- 異世界冒険作品：ファンタジー + アドベンチャー。戦闘が主要な見どころならアクションも付与。
- 学園ラブコメ：恋愛 + コメディ。青春時代の成長が中心なら青春も付与。
- スポーツ青春作品：スポーツ + 青春。人間関係や葛藤が作品の主要な軸ならドラマも付与。
- 推理サスペンス：ミステリー + サスペンス。恐怖を主な目的とする場合に限りホラーも付与。

## 3. ジャンルにしない分類

以下はジャンルとは別の属性・タグ体系にする。

| 分類軸 | 例 | 扱い |
|---|---|---|
| 舞台・場所 | 学園、学校、都市、田舎、宇宙 | 舞台タグ |
| 世界観・設定 | 異世界、近未来、現代、終末世界 | 設定タグ |
| 物語展開 | 転生、タイムリープ、復讐、成り上がり | 展開タグ |
| 物語構造 | 群像劇、ループもの、オムニバス | 構造タグ |
| 登場要素 | 魔法少女、吸血鬼、妖怪、超能力 | 要素タグまたはサブジャンル |
| 人間関係 | 友情、家族、師弟、三角関係 | 関係性タグ |
| 職業・活動 | 料理、医療、警察、教師、クリエイター | 職業・活動タグ |
| 対象・視聴層 | キッズ、ファミリー、全年齢等 | 対象層属性。ジャンルと混同しない |
| 作品形式 | TV、映画、OVA、ONA、SPECIAL、短編 | anime.format等の形式属性 |
| 配信・展開形態 | 劇場公開、テレビ放送、Web配信 | 配信・公開属性 |

## 4. サブジャンル・タグの階層

サブジャンルは、親となる大ジャンルに属し、そのジャンルの範囲を細分化する分類に限定する。

初期候補：

- アクション：格闘、剣戟、ガンアクション、ヒーローアクション
- アドベンチャー：探索、旅、宝探し、サバイバル冒険
- コメディ：ギャグ、パロディ、ブラックコメディ、シュールコメディ
- ドラマ：人間ドラマ、家族ドラマ、社会派ドラマ、心理ドラマ
- 恋愛：純愛、片思い、三角関係、ラブコメ
- SF：近未来SF、宇宙SF、サイバーパンク、ディストピア、AI
- ファンタジー：ハイファンタジー、ローファンタジー、ダークファンタジー、魔法ファンタジー
- ミステリー：本格推理、犯罪ミステリー、日常の謎
- サスペンス：心理サスペンス、クライムサスペンス、パニック、逃走劇
- ホラー：心霊、怪奇、サイコホラー、オカルト
- スポーツ：球技、格闘競技、陸上、水上、ウィンタースポーツ、モータースポーツ
- 日常：ほのぼの、癒やし、スローライフ、グルメ
- 青春：学園青春、部活動、青春群像劇、成長物語
- 音楽・芸能：バンド、アイドル、吹奏楽、クラシック音楽、ダンス
- 歴史・時代劇：日本史、世界史、戦国、幕末、古代文明
- 戦争・ミリタリー：近代戦、架空戦記、軍事戦略、兵器
- ロボット・メカ：巨大ロボット、リアルロボット、スーパーロボット、パワードスーツ

この一覧は候補であり、作品データへの割当テストと重複検査を終えるまで正式登録しない。横断的な特徴（例：タイムリープ、転生、異世界、群像劇）は、親ジャンルを持たないタグとして管理する。

## 5. 付与ルール

1. 原則として大ジャンルを複数付与できる。
2. 主要ジャンルは1〜2個を目安とし、副次ジャンルは作品の内容上必要な場合のみ追加する。上限を機械的に強制せず、過剰付与を管理者レビューで防ぐ。
3. ジャンルの付与は公式紹介文・公式サイト・信頼できる作品資料などの根拠に基づく。タイトルだけから自動確定しない。
4. 単に登場するだけの要素はジャンルにしない。物語上の中心性・継続性・作品の訴求点を確認する。
5. 作品形式や対象年齢をジャンルとして付与しない。
6. 外部データ由来の分類は原文・外部ID・出典を保持し、ANIXIA分類への対応付けを別途レビューする。
7. 判断できない作品は無理に分類せず、未分類・要確認として残す。

## 6. 偏りの監視

ジャンル数を均等にするのではなく、以下を定期集計する。

- 大ジャンル別作品数・構成比
- 公開作品と非公開候補を分けた集計
- 主要ジャンル別作品数と副次ジャンル別作品数
- ジャンルの組み合わせ（共起）頻度
- 未分類作品数・未分類率
- 1作品に付与されたジャンル数の分布
- サブジャンルごとの登録作品数
- 同じ意味の分類の重複候補

偏りが大きい場合は、まず付与漏れ・外部データのマッピング誤り・粒度の不統一を調べる。件数だけを理由にジャンルを統合・分割しない。

## 8. DB移行方針（未実施）

現在のgenresテーブルは大ジャンル・サブジャンルの階層を表すparent_id等を持たない。したがって、正式採用時には次のような設計を検討する。

- genres：大ジャンル・サブジャンルのマスター。slug、name、name_ja、description、parent_id、sort_order、is_active等。
- anime_genres：作品とジャンルの多対多関係。必要なら role（primary / secondary）を追加。
- tags：横断タグのマスター。
- anime_tags：作品とタグの多対多関係。
- genre_external_ids：外部分類IDとANIXIAジャンルの対応関係。対応の確度・根拠・レビュー状態を追加することを検討。

移行時は既存のgenre_external_idsとanime_genresを保持し、マッピング表を作成してから関連を移す。削除・統合・ID変更を一括実行しない。バックアップ、重複検査、件数比較、ロールバック手順を用意してから本番適用する。
